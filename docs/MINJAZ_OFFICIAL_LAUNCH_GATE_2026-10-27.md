# منجاز — بوابة الإطلاق الرسمي (27 أكتوبر 2026)

القرار: إطلاق حقيقي لسوق الخدمات (العميل ينشر الطلب، والمنفذ يقدم العرض)، مع الاحتفاظ **بجميع الخدمات والفئات الموجودة**. البريد الإلكتروني هو وسيلة التسجيل الأولية، وSMS غير مستخدم عند تفعيل سياسة البريد. المدفوعات آخر مرحلة **بعد** جاهزية البنية الأساسية.

## ما تحقق في المستودع
- إنشاء حساب باسم + بريد + جوال سعودي + كلمة مرور، رابط تحقق يُستخدم مرة واحدة، استعادة كلمة المرور، وحظر تسجيل الدخول قبل التحقق.
- خدمات منجاز الحالية (~50 خدمة في Seed الأصلي) مرتبطة بنشر الطلبات مع إمكانية اختيار قسم عام.
- حماية من تكرار نشر الطلب عند تكرار النقر/انقطاع الشبكة مع مفتاح Idempotency.
- مسار العميل، المنفذ، المحادثات، التقييمات، الطلبات، النزاعات، إدارة المحتوى والأرباح موجود في الكود وتحتاج اختبارات واقعية كاملة.
- فحص `/readiness` يمنع اعتبار النظام صالحًا تجاريًا إذا لم تكتمل الشروط.
- **تحذير مالي:** لا يوجد مزود تسويات Marketplace/Payouts مربوط يؤكد تحويل مستحقات المستقل. لذلك أضفنا `MARKETPLACE_PAYOUT_SETTLEMENT_NOT_IMPLEMENTED` ورفض تأكيد سحب «paid» يدويًا خارج preview؛ لا يجوز اعتبار دفعة لم تُحول فعليًا أنها وصلت.
- فحص قراءة مباشر: `python scripts/check_minjaz_launch_readiness.py`، وللموافقة التجارية الصارمة: `python scripts/check_minjaz_launch_readiness.py --base https://YOUR-VERIFIED-DOMAIN --commercial`.

## العوائق الأساسية التي تحتاج طرفًا خارج GitHub
1. **الهوية الرسمية:** تحديد هوية منشأة منجاز المصرح لها بالتعامل التجاري، ومراجعة اشتراطات السجل/وثيقة العمل الحر وتوثيق المتجر والحساب البنكي التجاري حسب نشاط المنصة. راجع https://mc.gov.sa/ar/mediacenter/News/Pages/29-03-23-02.aspx
2. **نطاق وهوية العلامة:** اختيار وربط نطاق HTTPS يملكه المالك (DNS وتحقق SSL)، ومنه عنوان إرسال بريد `no-reply@domain`.
3. **إرسال البريد الفعلي:** إنشاء مفتاح Resend مع Sender Domain مثبت وتعيين `EMAIL_MODE=resend` و`EMAIL_FROM` و`RESEND_API_KEY` و`ADMIN_EMAIL` و`PUBLIC_BASE_URL` داخل Railway، أو SMTP آمن. لا تضع المفاتيح في GitHub أو الدردشة.
4. **انتقال حسابات المستخدمين القدامى:** مراجعة حسابات الجوال القديمة، وتأمين ربطها بالبريد قبل تفعيل `EMAIL_AUTH_REQUIRED=1` حتى لا تفقد حساباتها. أضيف فحص تجميعي للقراءة فقط `scripts/audit_minjaz_legacy_accounts.py`؛ يجب تشغيله داخل بيئة مصرح لها بقراءة قاعدة بيانات المنصة **دون مشاركة أي مفاتيح أو بيانات حسابات** ثم مراجعة النتائج. وجود حساب نشط واحد غير متوافق مع البريد يجعل انتقال الحسابات غير جاهز.
5. **التخزين:** Bucket خاص لملفات الطلبات مع روابط مؤقتة ومنع مشاركة الملفات الخاصة.
6. **هوية المنفذين:** مزود KYC موثوق مناسب للعمل في السعودية وإجراءات الموافقة والتحقق.
7. **الامتثال:** شروط الاستخدام، الخصوصية، الاسترجاع/الإلغاء/النزاعات، قواعد الخدمات الطلابية المشروعة، بيانات المنشأة والتواصل، توثيق موافقات المستخدمين. راجع نظام حماية البيانات: https://dgp.sdaia.gov.sa/wps/portal/pdp/knowledgecenter/details/PDPL
8. **الدفع أخيرًا:** اتفاق تجاري وتقني مع مزود مرخص يدعم منصات الطرف الثالث، تحصيل المدفوعات، حفظ/توزيع المستحقات، استردادها، وربط webhook موقّع وتحويلات قابلة للمطابقة. لا تسمّ هذه البنية «ضمان/حجز أموال» بدون موافقة المزود القانوني وتحديد دور منجاز النظامي.
9. **النشر الرسمي:** اختبارات العميل والمستقل والمدير على أجهزة مختلفة، سجلات الأخطاء وحماية البيانات ونسخ احتياطي مستعاد تجريبيًا، تجارب دفع Sandbox، ثم انتقال مضبوط إلى الإنتاج ومراقبته.

## خطر فوري في Railway
مشروع MINJAZ الإنتاجي يحتوي **23 عملية حذف خدمات قديمة معلّقة**. لا تضغط `Accept deploy` أو تعتمد حزمة التغييرات دون تقييم الخدمة والتبعيات وأخذ نسخة احتياطية. مشروع التجربة منفصل؛ `minjaz-app-prod` مرتبط بفرع `main` الأقدم.

## مبدأ الترقية
- تمر الاختبارات الآلية أولا، ثم تشغيل نسخة Staging ذات خدمات وبيانات اختبار معزولة.
- اختبار وصول رسالة بريد فعلية وحساب العميل/المستقل/الإدارة، وعدم فقدان أو دمج حسابات غير موثقة.
- لا نغيّر `APP_ENV=production` ولا نعتمد المدفوعات إلا عندما ترجع `/readiness` نتيجة `ready_for_commercial_launch: true`، ويكون كل شرط مدعومًا **بدليل تنفيذ**.
- لا نضع `PAYMENT_MODE=mock` في أي بيئة مالية فعلية.

## تدقيق الحسابات القديمة — للقراءة فقط (قبل الترقية)

الأداة `scripts/audit_minjaz_legacy_accounts.py` لا تغيّر الحسابات ولا تنقلها ولا تطبع البريد أو الجوال أو المعرّفات، وتبدأ معاملة `READ ONLY`، وترفض التشغيل دون موافقة صريحة من المشغّل. نفذها داخل سياق تشغيلي موثوق لديه `DATABASE_URL` من إعدادات الاستضافة، ويفضل ببيانات اعتماد PostgreSQL **للقراءة فقط**:

```bash
python scripts/audit_minjaz_legacy_accounts.py --confirm-read-only
```

يعرض التقرير **أعدادًا فقط**: الحسابات النشطة والمحذوفة، الحسابات المسجلة بالجوال دون بريد، غير المفعلة، بدون كلمة مرور، ملفات التعريف غير المكتملة، أصحاب الجلسات النشطة المتأثرين، وعدد المستخدمين غير الجاهزين الذين لديهم طلبات، إن كانت بنية الطلبات متاحة. يتوقف إذا لم تُطبق أعمدة الهجرة المطلوبة 034 و035، ولا يشغّل أي ALTER أو UPDATE أو DELETE.

- `account_migration_required=true`: **ممنوع** قلب سياسة تسجيل الدخول في الإنتاج؛ يلزم مسار نقل حسابات يعتمد على إثبات ملكية الجوال القديم والبريد الجديد بشكل مستقل، وبموافقة المستخدم، مع مراجعة الحسابات والطلبات يدويًا عند التعارض. لا دمج تلقائي بناء على رقم جوال أو اسم أو بريد مدخل فحسب.
- `account_migration_required=false`: هذا لا يعني جاهزية الإطلاق أو وصول رسائل البريد؛ استكمل اختبارات إرسال البريد الفعلي وبريد المدير وسياسات الأمان وباقي بوابة الإطلاق.
- **الحالة الراهنة:** تمت إضافة الأداة واختبارها على قاعدة بيانات PostgreSQL مؤقتة داخل CI. **لم يُجر هذا التدقيق بعد على بيانات إنتاج منجاز، ولا توجد خطة نقل لحسابات قديمة معتمدة**. لا تضع أرقام الحسابات أو أي معلومات تعريفية في GitHub أو المحادثة.
